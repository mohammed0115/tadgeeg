# المرجع الذهبي — مواصفة التنفيذ

> 🔴 **المرجع الأساس: `main @ 3d29066` (4-8-2026).**
> الفرق المسموح **أربعة بنود مُعدَّدة** — `docs/MASTER.md` §١.٢.
>
> **شرط القبول:** كل سجل موجود يبقى بقيمه **حرفيًا** · والزيادة سجلات جديدة
> فقط. أي تغيّر في سجل قائم = انحراف غير مصرَّح به = الخطوة مرفوضة.

> **المسار الثاني · الحلقة ٣** · يحتاج بيئتك للتشغيل
> **الغرض:** إثبات أن أحكام التدقيق لم تتغيّر أثناء التفكيك

---

## ١. لماذا يجب أن يغطّي المنظومات الأربع

الجرد أثبت أن أربع منظومات حيّة تحكم على المستندات:

| المنظومة | تكتب في | المقياس |
|---|---|---|
| المدقق القديم → `merge_risk_assessment` | `Invoice.risk_score` · `Invoice.risk_level` | 3 مستويات · لا `critical` |
| المحرك النشط `RiskEngine` | `AuditRun.risk_score` · `AuditRun.risk_level` | 4 مستويات |
| `AuditEngine` القديم | مخرَج `run_full_pipeline` (مسار المستندات) | أوزان 40/25/10/5 |
| `journal_analytics` | نتائج تحليل القيود | `base_score` 25–50 |

مرجع يغطّي واحدة يسمح بتغيّر أحكام الثلاث الأخرى بلا اكتشاف.

---

## ٢. شكل السجل الواحد

```
{
  "document_id": "...",
  "document_type": "sales_invoice",

  "legacy": {
    "validation_score": 91.18,
    "rules_total": 34,
    "passed": ["INV-001", ...],
    "failed": ["DUP-004", ...],
    "computed_risk_level": "critical"        // من _score_to_risk — يُحسب ويُهمَل
  },

  "written": {                                // ما يُحفظ فعلًا على الفاتورة
    "risk_score": 78.0,
    "risk_level": "high",
    "is_duplicate": true
  },

  "engine": {
    "risk_score": 62.4,
    "risk_level": "high",
    "results": [{"rule_code": "DUP-02", "status": "fail", "severity": "critical"}, ...],
    "components": {"violation": 0.31, "amount": 0.12, ...}
  },

  "ias7": {
    "cash_flow_class": "operating",
    "cash_flow_subcategory": "op_supplies"
  },

  "agreement": {
    "levels_match": false,                    // written.risk_level == engine.risk_level ؟
    "shared_codes_agree": true,               // التسعة المشتركة تعطي نفس الحكم ؟
    "shared_code_conflicts": []               // أي رمز اختلف الحكمان عليه
  }
}
```

**الحقل الحاسم هو `agreement`.** هو الذي يحوّل سؤال «هل يتفق المحرّكان» من تخمين إلى نسبة.

## ٣. أمر التوليد — المتطلبات

`manage.py generate_golden_master`

```
--out          مسار الخرج (افتراضي tests/fixtures/golden_master.json)
--limit        عدد المستندات (افتراضي 200)
--org          تقييد بمنظمة واحدة (اختياري)
--seed         بذرة الاختيار العشوائي — إلزامية للتكرار
```

**شروط إلزامية على التنفيذ:**

1. **قراءة فقط.** لا يكتب على أي مستند ولا يُنشئ `AuditRun`. يستدعي منطق الحساب لا مسار الحفظ. مرجع يعدّل البيانات التي يقيسها ليس مرجعًا.
2. **اختيار ثابت.** `order_by("id")` مع بذرة، لا `order_by("?")`. عيّنة تتغيّر بين تشغيلين تجعل كل فرق غامضًا.
3. **تنوّع مقصود في العيّنة:** فواتير نظيفة · مكرّرة · بأخطاء ضريبة · بمستويات مخاطر مختلفة · من منظمتين على الأقل (لكشف تسرّب بين المستأجرين).
4. **يرفض العمل على `live`** — بنفس منطق `deployment/loadtest/audit_pipeline.py`.
5. **أرقام عشرية مثبّتة** — `round(x, 2)` في كل موضع. تعويم غير مقرّب يجعل المقارنة بايت ببايت تفشل على فروق لا معنى لها.

## ٥. الإثبات اليدوي قبل الاعتماد

لا تعتمد المرجع قبل أن تراه يفشل بيدك:

```bash
# 1. توليد
python manage.py generate_golden_master --seed 42 --limit 200
sha256sum tests/fixtures/golden_master.json

# 2. يجب أن يمرّ
pytest tests/test_golden_master.py -q

# 3. إثبات القدرة على الفشل — غيّر عتبة مؤقتًا
#    core/constants.py: HIGH_RISK_THRESHOLD = 70.0  →  69.0
pytest tests/test_golden_master.py -q        # يجب أن يفشل

# 4. أرجع القيمة
#    HIGH_RISK_THRESHOLD = 70.0
pytest tests/test_golden_master.py -q        # يجب أن يمرّ

# 5. نسبة التوافق
python -c "import json;d=json.load(open('tests/fixtures/golden_master.json'));\
m=sum(x['agreement']['levels_match'] for x in d);print(f'{m}/{len(d)}')"
```
