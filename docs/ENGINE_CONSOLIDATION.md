# توحيد محركات الحكم — إغلاق المرحلة الأولى

**الحالة:** مكتملة تقنياً على شجرة حذف معزولة من `dd1c528`، بانتظار مراجعة الشحنة ودفعها إلى `claude` فقط.

**النطاق:** حذف `AuditEngine` القديم وقواعده الثماني عشرة، مع إبقاء عقود البيانات الحية وحماية صفوف التدقيق التاريخية.

**خارج النطاق:** أي تعديل على `main`، إعادة تصميم نطاق قواعد V1، والهجرات أو الإعدادات أو بيانات التدقيق التاريخية.

## 1. القرار التنفيذي

كانت المشكلة المعمارية أن المستند الواحد يمكن أن يُحكَم عليه بخمس منظومات مستقلة، وبمقاييس خطر وأوزان مختلفة. هدف المرحلة الأولى ليس تفكيك كل الملفات الكبيرة، بل إزالة تعدد مسارات الحكم غير القابل للمراجعة وتثبيت نقطة دخول الرفع على V1. بعد توحيد مسار الرفع سابقاً وحذف المحرك القديم الآن، صارت البنية قابلة للتدقيق التقني: لكل مسار رفع محرك متوافق واحد، وتبقى الديون الكبيرة موثقة بدلاً من أن تُخفى.

| المقياس | قبل المرحلة الأولى | بعد هذه الشحنة | التغير |
|---|---:|---:|---:|
| منظومات الحكم | 5 | 3 | -2 |
| مخططات الترجيح | 4 | 3 | -1 |
| القواعد المصانة | 191 | 173 | -18 |
| وحدات AuditEngine المحذوفة | 0 | 8 | +8 |
| صفوف التدقيق التاريخية | محفوظة | محفوظة | 0 |

## 2. ما حُذف وما بقي

حُذف `apps/audit/audit_engine.py` وسجل قواعده ذي الثماني عشرة قاعدة، إلى جانب سبع وحدات قواعد موروثة. ونُظف `apps/audit/rules/__init__.py` من الاستيرادات والتصديرات التي تشير إلى الوحدات المحذوفة فقط؛ بقيت تصديرات `AuditRule` و`RuleResult` و`RuleStatus` و`Severity` كما هي، ولم يُضف أي `try/except` إلى مهيئ الحزمة.

| الفئة | النتيجة |
|---|---|
| منطق AuditEngine والتقييم والسجل | محذوف |
| قواعد R001–R018 الموروثة | محذوفة مع المحرك |
| `RuleResult` و`RuleStatus` و`Severity` | بقيت في `apps.audit.rules.base_rule` بهويتها الأصلية |
| أحكام ونتائج التدقيق المخزنة | لم تُمس |
| رفع الفواتير | يستدعي `run_audit_compat_task` مثبتاً على `engine_override="v1"` |

## 3. عقد التقرير الذي لم يُحذف

لم يكن `AuditReport` سلوك محرك؛ كان بنية بيانات يقرأها `_serialise_audit_report` في مسار المستندات. لذلك نُقل حرفياً إلى `apps/audit/reports.py`، مع تحقق AST يثبت تطابق تعريف الصنف قبل النقل وبعده. أضيف تلميح النوع فقط إلى مُسلسِل الأنبوب؛ لم يتغير أي حقل أو اسم بديل أو خاصية في العقد.

> `passed_count` و`failed_count` و`skipped_count` و`error_count` جزء من عقد المُسلسِل، لا تفضيل تسمية لمحرك محذوف.

اختبارات `test_documents_path_parity.py` الخاصة بعقد التقرير مرت بعد النقل دون تغيير لأي assertion. أما حالات اختبار نطاق القواعد فقد حُذفت لاحقاً بقرار منفصل لأنها كانت تختبر حصراً `AuditEngine.evaluate` و`REGISTERED_RULES` و`AuditRule.is_applicable` للمحرك الذي زال، لا عقد التقرير المنقول.

## 4. الحراس والاختبارات التي تغيرت

لم يُحذف اختبار لأنه فشل فقط. صُنفت كل حالة حسب السلوك الذي تحرسه وحارسها البديل، ثم اتخذ قرار صريح لكل فئة. حارس غياب الوحدة حل محل قائمة مستدعين فارغة حتى يفشل الاختبار إذا عاد الملف مستقبلاً. كما بقيت اختبارات الرفع والجلسات التي تنفذ HTTP فعلياً؛ أزيل منها decorator قديم كان يرقّع `run_audit` المحذوف ووسيطه فقط، من دون تغيير assertions أو إضافة محاكاة بديلة.

| الفئة | الإجراء | سبب القرار |
|---|---|---|
| عقد `AuditReport` | نُقل إلى `reports.py` | عقد حي لمسار المستندات |
| نطاق `REGISTERED_RULES` و`is_applicable` | حُذف ست حالات | عقد خاص بـAuditEngine بلا نظير V1 قائم |
| DSL داخل AuditEngine | حُذفت حالتان | تكامل محرك محذوف؛ DSL محروس باختبارات مستقلة |
| API «30 قاعدة» | حُذفت حالة واحدة | كانت patch ثم `pass` بلا HTTP أو assertion |
| جلسة التدقيق ومنع التكرار | بقي اختباران | حراس أحياء للرفع الحقيقي؛ اجتازا دون ترقيع المحرك |
| واجهة الحالات | حُذفت حالات المحرك فقط | بقيت اختبارات تطبيع/رفض/تخزين وحدود الواجهة |

## 5. بوابة التحقق النهائية

نتيجة البوابة النهائية هي **4030 ناجحاً و4 متخطاة و18 اختباراً فرعياً ناجحاً**. الإخفاق الوحيد هو `test_compiled_catalogue_is_not_stale`، وهو فشل mtime بيئي معروف بين `django.po` و`django.mo` بفارق أجزاء من الألف من الثانية؛ لا يتصل بحذف AuditEngine ولا غُيّر هذا الاختبار ضمن الشحنة. فحص الهجرات أعاد `No changes detected`. فحص `check --deploy` عاد بالتحذيرات القائمة للمشروع، لا بأخطاء جديدة للحذف.

| الفحص | النتيجة | الحكم |
|---|---|---|
| `pytest -q --no-cov` | 4030 passed، 1 mtime بيئي، 4 skipped | اجتاز وفق قرار الشحنة |
| حارس غياب AuditEngine | ناجح | لا يمكن عودة الوحدة صامتة |
| حارس جلسة الرفع ومنع التكرار | 2 passed | مسار حي بلا ترقيع AuditEngine |
| ميزانية المعالجات الصامتة | 5 passed | الميزانية 284 → 273 |
| `makemigrations --check --dry-run` | No changes detected | لا هجرة مفقودة |
| `check --deploy` | تحذيرات قائمة | لا مانع جديد من الحذف |

## 6. ميزانية المعالجات الصامتة

استُخدم معيار AST نفسه الموجود في `tests/test_silent_exception_budget.py`، لا عدّ نصي لكلمة `except`. كان العد قبل الحذف 282 وبعده 271؛ أي نقص حقيقي مقداره 11. وجميع المعالجات الإحدى عشرة كانت داخل ملفات القواعد المحذوفة، مع صفر تغير في الشيفرة الباقية. لأن السقف التاريخي كان 284، خُفض إلى **273 = 284 - 11** فقط؛ لا يزداد السقف ولا يُخفى الفرق برفعه.

| التحقق | القيمة |
|---|---:|
| العد قبل الحذف | 282 |
| العد بعد الحذف | 271 |
| النقص المنسوب للملفات المحذوفة | 11 |
| النقص خارج النطاق المحذوف | 0 |
| السقف قبل/بعد | 284 / 273 |

## 7. قياس الرفع الفعلي

أعيد رفع المدخل نفسه عبر نقطة API الرسمية، بنفس قاعدة SQLite وبنفس بصمة SHA-256، مع `refresh_from_db()` لقراءة السجلات المحفوظة. طابقت الحقول العشرة جميعاً مرجع ما قبل الحذف، بما في ذلك `blocks_approval` و`engine_version`، وهي حقول لا تثبتها اختبارات الوحدة وحدها.

| الحقل | قبل الحذف | بعد الحذف |
|---|---:|---:|
| `validation_score` | 70.59 | 70.59 |
| `rules_failed` | 10 رموز | القائمة نفسها |
| `is_duplicate` | false | false |
| `risk_score` / `risk_level` | 50.0 / high | 50.0 / high |
| `blocks_approval` | true | true |
| `engine_version` | 2.0 | 2.0 |
| `subtotal` / `total_amount` / `vat_amount` | 1000 / 1150 / 150 | 1000 / 1150 / 150 |

نظفت المؤسسة والسجلات التي أنشأها القياس. بقي مستخدم اختبار واحد بسبب عدم حذف المؤسسة له تلقائياً، فحُذف بالعنوان المحدد للقياس فقط؛ انتهت العدادات إلى صفر للمؤسسات والمستخدمين والفواتير والمستندات وعمليات التدقيق ونتائج التحقق.

## 8. الديون والحدود المتبقية

لا يحل الحذف محل التفكيك المؤجل لـ`page_views.py` أو توحيد جميع المخططات. الأهم بعد هذه الشحنة هو أن V1 لا يملك حارس نطاق مكافئاً لعقد `REGISTERED_RULES`/`is_applicable` القديم. هذه فجوة موثقة ولا تُعالج هنا، لأن اختراع عقد V1 في شحنة حذف سيصنع تغطية ظاهرية ويخلط شحنتين مختلفتين.

> **بند لاحق عالي الأولوية:** فحص ما إذا كان Rule Engine V1 يحتاج عقد نطاق صريحاً وحارساً مخصصاً؛ ليس جزءاً من حذف AuditEngine.

## 9. دروس المراجعة والانحرافات المسجلة

كشفت الشحنة ثلاثة أنواع من جرد غير كافٍ: فحص الاستيراد الحرفي أهمل اختبارات `tests/`، ولم يميز بين عقد بيانات داخل ملف محرك وبين المحرك نفسه، ولم يفحص `__init__.py` الذي يستورد وحدات الحزمة المحذوفة. لذلك، قبل حذف وحدة مستقبلية، يجب جرد التطبيق والاختبارات ومهيئات الحزم بالـAST، ثم فحص المحتوى بعد أي دمج متوازٍ لا مجرد سجل الحذف.

كما تسجل المراجعة الانحرافات التالية: خط أساس موروث غير موثق (`4,076`) استُبدل بقياس 4,053؛ وصف «14 applies_to» كان غير دقيق؛ ومرجع قياس سابق وُضع في `/tmp` بدلاً من `docs/`. هذه الشحنة تحفظ كل أدلة المقارنة في `docs/` وملفات المراجعة الدائمة، ولا تعتمد على ملف مؤقت.
